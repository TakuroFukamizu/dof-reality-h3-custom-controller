# 安全設計

人が乗る装置なので、非常停止はソフトウェアだけに依存させない。ここでは採用予定の機能ブロックと確認事項を整理する。「具体回路が完成した」という意味ではない。

## 停止手段の階層

| 階層 | 手段 | 担当 |
| --- | --- | --- |
| 軸ごとの通常停止 | 位置制御で減速・停止 → 位置制御で保持したままブレーキ給電 OFF → `BRAKE_APPLY_WAIT_MS` → PWM 0 → 主電源 OFF 指令（[protocol.md](../control-server/protocol.md) §3.1 DISARMING。PWM を先に 0 にすると、ブレーキが効くまでの間に荷重で動く） | 各 CoreS3 |
| 軸ごとの異常停止 | FAULT ラッチ。PWM 停止、ブレーキ給電 OFF、主電源指令 OFF。再始動は明示的解除と再 ARM | 各 CoreS3 |
| 全軸停止（PC 経由） | 1 軸が異常停止したら PC が残り 2 軸も停止させる（3 軸は機械的につながっている） | PC |
| 全軸停止（ハード） | 物理非常停止ボタン → 共通駆動許可回路 → 主電源リレー（24V 電源の AC 入力）を遮断 | 独立回路（詳細未確定） |

## 主電源リレーのインターロック

```text
物理非常停止ボタン（NC 接点）
        │
        ▼
共通の駆動許可・停止回路【具体回路は未確定】
   ← CoreS3 3 台の駆動許可（3 台すべて正常で成立）
        │
        ▼
既存電源基板の DC_STOP1 緑 → R1 15kΩ → Q1 → HRS4H
        │ AC を開閉
        ▼
既存 24V モーター用電源 → 3 軸
```

- 3 台の CoreS3 の GPIO を単純に並列接続して緑線を駆動しない。3 台すべての準備完了と非常停止解除が成立したときだけ投入を許可し、いずれかが異常なら許可を取り消す独立したインターロックにする。
- 現状の試験構成では 1 台の G2 から主電源リレーを直接制御している。**主電源投入で他軸の 24V も入る**ため、単軸試験では未試験軸を電力側で切り離す。
- GPIO 初期状態は駆動禁止。USB 通信断や異常検出時は駆動禁止。
- 既存 HRS4H が非常停止用の安全規格に適合しているかは未確認。AC を遮断しても 24V 電源の出力コンデンサに残ったエネルギーでモーターが動きうる。必要に応じて安全リレーや適切な電源遮断器を追加する。
- 電源遮断時に機構がどう動くかを無人で確認してから、有人運転の判断をする。

## ブレーキの操作順序

ブレーキは 24V 通電で解除、無通電で作動。

```text
待機      : ブレーキ給電 OFF、モーター駆動禁止
解除準備  : ブレーキに 24V 給電 → 解除待ち時間（実測して設定）
駆動      : エンコーダ監視を有効にして駆動
通常停止  : モーターで減速、エンコーダで停止を確認
保持へ    : ブレーキ給電 OFF → 作動待ち時間（実測して設定）→ 駆動禁止
```

- 通常停止では回転中に機械ブレーキを掛けることを前提にしない（動的制動の可否が未確認）。
- 解除してから荷重をモーターが支えるまでの間、および停止後にブレーキが作動するまでの間に機構が動かないようにする。PWM = 0 でブレーキを解除するだけで動く場合は試験を中止し、支持方法を変える。
- 解除状態を読み返すセンサーはない。画面は「解除指令中」と表示し「解除済み」と断定しない。
- ブレーキとモーター駆動のインターロック（ブレーキ作動中に PWM を出さない）を設ける。
- 停止確認の「カウント変化なし」は断線時にも成立する。センサー異常時はこの判定を確実な停止確認に使わない。

## 各軸のソフトウェア安全機能

- エンコーダ異常（断線、計数エラー）、追従誤差、速度超過、通信断、制御周期異常の検出。
- 時間上限、Duty 上限、相対移動上限、無変化タイムアウト。センサーが変化しなくても Duty を自動で上げない。
- PC 通信途絶時の PWM 停止。USB 操作にはハートビート（リース）を必須にする。
- ウォッチドッグ。UI や USB の詰まりが駆動上限時間を延長しないよう、期限監視は独立した高優先度の周期処理にする。
- 可動範囲制限と原点復帰。インクリメンタルエンコーダのため起動時の絶対位置は不明。任意の位置をゼロにするだけでは可動限界を保証できない。元機の「可動端まで動いて中央へ戻る」キャリブレーションをいきなり再現せず、外部の基準位置と可動範囲の測定から設計する。
- 電流監視（VIOUT）はソフト上の過電流検出に使うが、過電流保護の唯一の手段にしない。感度・ゼロ点が未校正の段階で「10A を超えたら停止」のような閾値を確定しない。

## ハードウェア側の安全条件

- 電源投入・リセット・書き込み中の GPIO はファームウェアで保証できない。MD13S の PWM 入力にプルダウン、リレーモジュールの IN にオンレベルと逆のプル抵抗を外付けし、ハードウェアの駆動許可が成立するまで MD13S に電力を供給しない。
- MCU の再起動・フリーズ・USB 断線でも駆動を許可し続けない仕組み（独立したウォッチドッグ回路や安全リレーで、周期信号が失われたら駆動許可を遮断）を候補にする。
- CoreS3 の内蔵バッテリーで駆動許可を保持しない。主電源が失われたことを検知できる構成にする。
- 初回試験では、モーター用 24V を物理的に切断し、必要なら リレー駆動入力も切り離した状態でファームウェアの挙動（勝手に動かない・解除しない）を確認する。

## GND と電源の分離

- 既存構成では Protection Board の信号 GND とモーター電源 GND が共通で、制御系とモーター系は絶縁されていない。GND 共通そのものが誤りではなく、モーターの大電流やノイズが制御配線・USB へ流れる経路を作ることが問題。
- 新構成では PC に USB ×3 でつながるため、PC 経由の GND 経路も加わる。元の集中制御基板より注意が必要。
- 対策の方向: 細い信号 GND やセンサー GND をモーター電流の戻り経路にしない。信号線を電力線と束ねない。レベルシフタ・分圧は絶縁ではないことを前提に、必要なら USB アイソレータや絶縁 I/O を検討する。
- 既存 5V と CoreS3 の 5V を並列接続しない。CoreS3 への給電経路と逆流防止を整理するまで、Grove 赤線を既存 5V に結ばない。

## 試験の実施条件

- 無人。機構を支持し、可動端から余裕を取る。
- 物理的な停止手段（主電源の遮断）を操作できる位置で行う。
- 初回は低 Duty（5%）・短時間（100ms）・1 方向 1 回。結果を見て次の Duty だけを決める。自動反復・自動増加・自動延長はしない。
- 動いてもカウントが変わらなければ Duty を上げず、入力配線・レベル変換・PCNT 設定を確認する。カウント 0 は「動いていない」と「入力を拾えていない」を区別できない。
- 異常注入（USB 切断、センサー異常など）はまず疑似入力・モーター非通電で試験する。
