3 軸を同時に動かしたのは最後の 1 回（上限へ・中立へ）だけで、手動往復は #3 + #2 の 2 軸。#1 の CoreS3 がホットプラグ直後からシリアルに応答せず、ユーザーがリセットするまで（17:38）使えなかったため。

**判明した問題（ファーム側の調整が必要、未修正）**

1. **「中立へ」を下から上がる向きで始めると #2 は「遅すぎ」で失敗する。** 比例制御で Duty が 8 % 台に落ちた時点（残り誤差 834）で速度が 500 → 200 → 150 count/s 未満になった。上から降りる向き（上限へ → 中立へ）は 3 回とも到達。Duty の下限 7 % が #2 の持ち上げ側の始動閾値より低い。
2. **#3 の「中立へ」が到達帯の縁で収束しないことがある。** 目標 3069 に対し 3077–3078（帯内）と 3080（帯外）を 36 s に 213 回往復。帯 ±10 に入っても 200 ms 居続けられず、ヒステリシスが無い。他の 4 回の #3 中立は収束しており、位置が帯の縁に乗ったときだけ起きる。ファームの時間上限 `MOVE_TIMEOUT_MS` は 45 s で、今回はスクリプトの 40 s が先に効いた。
3. **手動速度の反転直後に「遅すぎ停止」が誤って働く。** +9 → −15 を途中 0 を挟まず送ると 100 ms 後に `WARN manual_slow`。速度窓が反転をまたいで速度を測っている。スクリプト側で反転時に 0.25 s の `S 0` を挟んだ後は 118 回の速度変更で警告 0。ファームは速度の符号が変わったら窓を取り直すべき。
4. **30:ED の `#2` 枠に #3 の校正値（6138 / 3069）が残っている。** 電源 OFF で `M 2` → `UNCAL` で消す。

**観察（問題ではないが記録）**

- #3 は `B 0`（ブレーキ作動）の応答で count 49、直後の `R 0` の応答で count 87。ブレーキ作動後に 38 カウント動いた。
- 17:10 の #3 校正の前、電源 入 から 4 s での「下限へ」は両方向とも無パルスで失敗し、12 s 後は動いた（acceptance_homing.md 参照）。今回の 3 軸運転では電源は入れっぱなしだったので再現確認はしていない。
- ホスト側でシリアルポートを閉じた直後にボードが USB に応答しなくなる、という従来の見立ては今日のデータでは支持されない（詳細の「USB」参照）。

### 使ったコマンド

ファームのシリアル（115200）: `?`（STAT / ENC 行）、`R 1|0`（主電源リレー）、`B 1|0`（ブレーキ解除 / 作動）、`S n`（手動速度 %）、`X`（停止）、`HOME` / `UPPER` / `NEUTRAL`（自動移動）。自動移動は `AUTO <kind> <phase> <reason> pos=` で完了・失敗を返し、移動中は 500 ms ごとに `ENC` 行を出す。

スクリプトは各ポートを DTR=1 / RTS=1 で開き、開いたまま保持する。自動移動は `AUTO ... done|failed|cancelled` か `ERR auto_` を待ち、`done` 以外ならその軸に `X` を送って以後の手順から外す。

### USB・シリアルについて

- #1（1C:DB）は 17:19:18 にホットプラグで直挿しポートに現れ、ロガーが開いて `?` を 0.5 s ごとに送ったが、12 s 以上一度も応答しなかった（ログに STAT / ENC 行が無い）。その後 17:19〜17:34 の 4 回の問い合わせも空応答。ユーザーのリセット後（17:38）は正常。**ポートを閉じる前から応答していなかった**ので、「ホストがポートを閉じると固まる」という見立ての証拠にはならない。

- 同日 16:58:59 と 17:18:32 に 30:ED の「Device not configured」が記録されているが、どちらもユーザーが 3 台構成に配線し直していた時間帯で、ケーブルの抜き差しと考えるのが自然。acceptance_homing.md の「USB が応答しなくなった 3 回目」は言い過ぎだった。
